# ADR 0002: External authentication adapter and internal identity

Status: Accepted

## Decision

Treat an OIDC-compatible provider as the production identity authority while maintaining internal User, ExternalIdentity, Workspace, WorkspaceMember, UserPreference, and SessionActor contracts. A constrained development provider exists only when `NODE_ENV` is not production and `AUTH_MODE=development`.

Session cookies contain only internal identity references, role, issued/expiry times, and a session identifier. They are HMAC signed, HTTP-only, same-site strict, secure in production, and short-lived. Domain services receive a resolved SessionActor rather than raw provider claims.

## Consequences

Provider migration does not rewrite internal ownership. First authenticated use creates one workspace and owner membership atomically. OIDC assurance requirements for billing-sensitive actions remain a later billing concern; the seam is explicit now.

## S18 reconciliation: production session exchange (2026-09-06)

The original adapter alone did not provide an OIDC-to-internal-session route. The implemented gateway boundary is now `POST /api/v2/auth/oidc`, enabled only in OIDC mode. It accepts a compact signed ID token (maximum Authorization header length 8192) in `Authorization: Bearer <ID token>`, with an exact `Origin: APP_ORIGIN` header. Tokens must never be sent in URLs, HTML forms, analytics, logs or persistent browser storage. No cross-origin CORS access is granted.

The same-origin deployment gateway owns provider initiation, authorization code/PKCE exchange, browser-bound state/nonce validation and registered return destinations. After that flow, the gateway's same-origin completion code invokes this endpoint with credentials included, checks the standard success envelope, discards its temporary credential and navigates to the fixed `data.redirectTo` value `/app`. A server-side gateway may instead forward the returned Set-Cookie header to the same browser over HTTPS. It must not assert Origin on behalf of arbitrary cross-origin requests. Strip untrusted forwarded-address headers at the public ingress; the existing distributed public limiter applies ten exchanges per minute per trusted address in deployed environments. Local synthetic-test rate limits remain unchanged.

Mythra verifies the signature using only the configured JWKS, exact issuer and configured audience, mandatory subject/expiry/issued-at claims, non-future issue time, increasing expiry and matching authorized party when supplied. Additional unconfigured audiences reject. Issuer and JWKS URLs require HTTPS outside local testing. It resolves/provisions the existing internal user/workspace and issues a fresh eight-hour signed internal session; it does not store provider tokens or introduce a refresh-token store. The no-store response contains only the fixed navigation target and the standard request ID, not an internal or external token in JSON. Failures issue no cookie.

Correction to the historical cookie sentence above: the existing implementation uses **SameSite=Lax**, not Strict. The production exchange retains Lax plus exact-origin POST protection, HttpOnly, Secure and Path=/; the existing session key rotation/expiry and database role re-resolution remain authoritative. The development endpoint remains unavailable in deployed/OIDC mode. A custom callback UI, provider registration and live deployment wiring are external integration prerequisites, not evidence that this repository has authenticated against a real provider. Verify those deployment prerequisites separately before production rollout.
